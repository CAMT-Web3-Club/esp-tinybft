## สรุป

- **Safety ผ่าน:** ไม่พบกรณีที่ replica ที่ถูกต้องสองตัว execute ต่างกัน, execute ซ้ำ หรือข้าม seqno ภายใต้ crash, reboot และ message loss simulator ทุกรอบผ่านเช็ค (a) state, (b) exactly-once และ (d) skips และ sanitizer ไม่รายงานอะไร
- **ไม่พบ memory corruption หรือ stack overflow:** role task ใช้ stack ราว 6 KB จาก 8 KB ตอนบูต heap ที่ใช้ได้จริงบน ESP32-C3 อยู่ราว 104 KiB ตอนบูต และเพิ่มอีก 14 KiB หลัง scheduler เริ่ม ไม่ใช่ 49 KB ตามที่ AGENT.md เขียนไว้
- **การทดลองในสภาพปกติยุติธรรม:** เมื่อไม่มี loss ทั้งสอง transport ส่งข้อความโปรโตคอลชุดเดียวกันต่อ request config ของ UDP กับ ESP-NOW ต่างกันแค่บรรทัด node กับ multicast
- **ปัญหาหลักคือ liveness เมื่อมี loss และเหลือ replica พอดี 2f+1:** View_change ไม่ถูกส่งซ้ำ และ state fetch เล็ง checkpoint ที่ไม่มี replica ไหนส่งให้ได้ A กับ B พบสองข้อนี้เองแยกกัน cluster ค้างนานหรือค้างถาวร
- **การวัดผล:** timeout ใน menuconfig ไม่มีผลจริง, retransmission เกิดจาก latency ได้ไม่ใช่จาก loss อย่างเดียว และ `analyze.py` คัด run ที่มี view change ออกไม่ได้ถ้ามีแค่ log ของ client

## Liveness และความเสถียร

### L1 (สูง) View_change ส่งครั้งเดียว ไม่ส่งซ้ำ

**ที่:**
- `src/tbft_replica.c:867-881`: `handle_vtimer` ส่ง View_change ซ้ำเฉพาะเมื่อ f+1 peer ยังทำงานปกติ ถ้าไม่ใช่จะขยับไป target+1
- `src/tbft_replica.c:1977`: `handle_status` จบทันทีเมื่อ replica อยู่ใน view change
- `src/tbft_replica.c:2465`: timer เพิ่มเป็นสองเท่าทุกรอบ สูงสุด 60 เท่า
- `src/tbft_view_info.c:42`: เก็บเฉพาะ View_change ใหม่สุดของแต่ละ replica

**อาการ:** ถ้า View_change ของ replica ตัวใดหายระหว่างทางไป primary ใหม่ รอบนั้นล้มเหลวและไม่มีใครส่งซ้ำ ทุกตัวต้องรอ timer ที่ยาวขึ้นเป็นสองเท่า แล้วขยับไป view ถัดไป ซึ่งอาจข้าม primary ที่ยังทำงานอยู่

เมื่อมี replica ตาย f ตัว ต้องได้ View_change จากทุกตัวที่เหลือ โอกาสสำเร็จต่อรอบจึงราว 66% ที่ loss 10% และราว 41% ที่ loss 20% replica ที่ timeout ก่อนเพื่อนจะขยับไป view ที่สูงกว่า View_change ของมันจึงหายไปจาก view ที่ตัวอื่นกำลังรวมกันอยู่ PBFT ต้นฉบับส่ง View_change ซ้ำผ่าน status จนกว่าจะได้ New_view

**หลักฐาน:** S3b (kill node0 กับ node1)
- loss 12–20%: liveness FAIL 8 จาก 8 รอบ (seed 104, 105, 110, 111, 112, 200, 209, 213)
- loss 10%: seed 206 FAIL ส่วน seed 102 ผ่าน
- seed 206: primary ของ view 2, 3, 9 และ 10 ได้ View_change 4 จาก 5 ฉบับที่ต้องการ
- seed 209: วนไปถึง view 20
- ไม่มี loss (seed 208): ผ่าน
- partition 60 s (seed 205): หลังเชื่อมต่อกลับ cluster ว่างอยู่ 32.7 s จนกว่า timer ที่ยาวขึ้นจะหมด บนบอร์ดเท่ากับราว 5.5 นาที

**แนวทาง:**
- ระหว่าง `in_progress` ให้ส่ง View_change ของ target ปัจจุบันซ้ำทุก Status period หรือใส่ bitmap ของ View_change ที่มีอยู่ใน Status เพื่อให้ peer ส่งเฉพาะฉบับที่ขาด
- primary ใหม่ส่ง New_view ซ้ำให้ replica ที่ Status บอกว่ายังรอ view นั้น

### L2 (สูง) fetch เล็ง checkpoint ที่ไม่มีใครเสิร์ฟได้

**ที่:**
- `src/tbft_state.c:170-174`: image ถูกเขียนทับทุกครั้งที่ทำ checkpoint
- `src/tbft_state.h:173`: เสิร์ฟ fetch เฉพาะ `image_seqno` ที่ตรงกัน
- `src/tbft_replica.c:886-904`: `fetch_timeout` เปลี่ยน target เฉพาะเมื่อรวม Checkpoint ได้ 2f+1 ฉบับเอง
- `src/tbft_replica.c:622`: `start_fetch` ไม่รับ seqno เดิมหรือต่ำกว่า
- `src/tbft_replica.c:2280`: replica ที่กำลัง fetch ไม่ execute
- `src/tbft_replica.c:1382` และ `:759`: แต่ยังส่ง Prepare และ Commit
- `src/tbft_replica.c:628`: replier ตัวแรกคือ primary

**อาการ 1 (replica ยังอยู่ครบ):**
- counter ทำ checkpoint ทุก 2 request พอ quorum ทำ checkpoint ถัดไป ก็ไม่มีใครเสิร์ฟ target เดิมได้อีก
- fetcher วนถาม replier ไปเรื่อยๆ จนกว่าจะรวม Checkpoint 2f+1 ฉบับของอันใหม่ได้ ระหว่างนั้นไม่ execute แต่ view-change timer ยังเดิน
- ผลคือเกิด view change ที่ไม่จำเป็น ถ้า fetcher เป็น primary ก็จะถูกเปลี่ยนออก

**อาการ 2 (เหลือ 2f+1 พอดี, ค้างถาวร):**
1. fetcher ยังส่ง Prepare และ Commit ทำให้อีก 4 ตัว execute ต่อได้อีกสอง checkpoint
2. สอง checkpoint นั้น stable ไม่ได้ เพราะขาด Checkpoint ของ fetcher
3. image ของทุกตัวเลย target ไปแล้ว จึงไม่มีใครเสิร์ฟ target ได้
4. window เต็ม และ New_view ทุกฉบับต่อจากนี้มี `min` เท่าเดิม cluster จึงค้างถาวร

**หลักฐาน:**
- S6b ใช้ timeout แบบบอร์ด (30/5/10 s) loss 20% ทั้ง 7 ตัวยังอยู่ (seed 211): liveness FAIL fetch 38 ครั้ง timeout 23 ครั้ง node0 ซึ่งเป็น primary fetch อยู่ 72 s แล้วถูกบังคับ view change
- seed 207: node4 ขอ checkpoint 8 เก้าครั้ง ขณะที่ image ของทุกตัวอยู่ที่ 10
- loss 10% ทั้ง 7 ตัว (seed 210): ไม่เกิด view change
- อาการ 2 ได้จาก code trace ยังไม่ได้ทำซ้ำ ต้องสร้าง scenario ใหม่ที่ kill สองตัวระหว่างที่มีตัวหนึ่งกำลัง fetch

**แนวทาง (เลือกอย่างใดอย่างหนึ่งหรือทั้งสอง):**
- (ก) แบบ PBFT: replier ตอบ fetch ด้วย seqno ของ image ที่ตัวเองมี และ fetcher ยอมเปลี่ยน target ไป checkpoint ที่มี Checkpoint ตรงกัน f+1 ฉบับ (weak certificate) วิธีนี้แก้ deadlock ได้ เพราะอีก 4 ตัวมี Checkpoint อย่างน้อย f+1 = 3 ฉบับ
- (ข) เก็บ image ของ stable checkpoint เพิ่มอีกชุด เพื่อให้เสิร์ฟ target ที่ stable ได้เสมอ counter ใช้ static เพิ่ม 8 × 1024 = 8 KB

### L3 (กลาง) `prep_view` ค้างหลัง `nv_install` ทิ้ง body

**ที่:**
- `src/tbft_replica.c:751`: บันทึก `prep_view` แม้หลังส่ง View_change ไปแล้ว
- `src/tbft_replica.c:1709`: ทิ้ง body ที่ n ≤ h หรือ n > max แต่ไม่ล้าง `prep_view`
- `src/tbft_replica.c:2435`: View_change รายงาน `prep_view`
- `src/tbft_replica.c:570`: Status ส่งซ้ำเฉพาะ Pre_prepare ของ view ปัจจุบัน

**ลำดับเหตุการณ์:**
1. backup ส่ง Prepare แล้วส่ง View_change จากนั้นจึง prepared ที่ seqno n เพราะ Prepare ของตัวอื่นมาช้า
2. NV(v+1) ไม่มี n ทุกตัวจึงทิ้ง body ที่ n แต่ยังเก็บ `prep_view = (v, d)` ไว้
3. primary ของ v+1 crash ก่อนจะใช้ n
4. View_change ของ v+2 รายงาน (v, d) ที่ n และ NV(v+2) เสนอ d ที่ n ซึ่งไม่มีใครถือ body
5. n จึง execute ไม่ได้ตลอดไป เพราะ execute ตามลำดับ และทุก view ต่อจากนี้เกิดซ้ำแบบเดิม

**แนวทาง:** ใน `nv_install` ขั้นที่ 2 ให้ล้าง `prep_view` และ `prep_digest` ของ slot ที่ทิ้ง body ทำได้อย่างปลอดภัย เพราะ NV(v+1) พิสูจน์แล้วว่า n ไม่ได้ commit ใน view ใด ≤ v: replica ไม่ส่ง Commit หลังส่ง View_change และ quorum ต้องตัดกัน

**ความมั่นใจ:** possible ได้จาก code trace ต้องเกิด primary crash สองครั้งพร้อมจังหวะเฉพาะ

### R1 (กลาง, ต้องจงใจสร้างข้อความ) `handle_fetch` อ่านนอกขอบเขต

**ที่:** `src/tbft_replica.c:2021` และ `:2052-2074`

**อาการ:**
- `index` ถูกตรวจแค่ว่า ≥ 0 จากนั้น `index * pchildren` overflow ได้ แล้ว `ptree[level+1][cidx]` อ่านนอกขอบเขตและส่งข้อมูลนั้นกลับไปให้ผู้ส่ง
- ตัวอย่าง: index 78090314 ทำให้อ่านข้อมูลราว 1 KB ก่อน tree รวมถึง reply ที่ cache ไว้
- ค่าอื่นทำให้เกิด load fault แล้วบอร์ด reboot

**แนวทาง:** ปฏิเสธเมื่อ `index >= tbft_ptree_nodes_at_level(level, pchildren)`

### ข้อระดับต่ำที่เหลือ

- **R2:** Meta_data ระดับ 0 ที่ seqno ไม่ตรงทำให้ fetch จบก่อนเวลา จากนั้น digest ไม่ตรงจึงต้อง fetch ใหม่ (`src/tbft_replica.c:2104-2124`, `src/tbft_state.c:262-283`)

- **R5:** exec callback ได้ `out.size = 0` จึงไม่รู้ความจุของ reply และตรวจขนาดหลังเขียนไปแล้ว (`src/tbft_libbyz.c:996`, `src/tbft_replica.c:796-809`)
- **R6:** `fetch_queue[TBFT_MAX_STATE_BLOCKS]` ขาดไปหนึ่งช่องเมื่อใช้ block เต็มจำนวน คือ root บวกทุก leaf (`src/tbft_state.h:61`) ทำให้ต้อง fetch รอบที่สอง counter ใช้ 5 จาก 8 block จึงไม่โดน
- **R7:** ขนาดของ Data (64 + `TBFT_BLOCK_SIZE`) และ New_key ตรวจแค่ตอนรัน (`src/tbft_replica.c:2030-2035`, `:2481-2487`) ควรเป็น `static_assert`
- **R8:** ระบบยอมรับ `num_replicas > 3f+1` แต่ quorum ยังเป็น 2f+1 ถ้า n ≥ 4f+2 quorum จะไม่ตัดกัน (`src/tbft_libbyz.c:223`, `:302`; `src/tbft_replica.c:163-164`) ค่าที่ใช้อยู่คือ f=2 กับ 7 replica ถูกต้อง
- **R9:** reply cache จับคู่ด้วย rid อย่างเดียว ถ้า NVS ใช้ไม่ได้ epoch จะเริ่มที่ 0 ทุกครั้งที่บูต client ที่บูตใหม่จึงอาจได้ reply เก่าของ rid เดิม ควรให้ `Byz_init_client` ล้มเหลวแทน
- **R10:** การคำนวณ MAC ของ softAP ทดเลขไปถึง byte 4 แต่ IDF บวกเฉพาะ byte สุดท้าย (`src/tbft_transport_espnow.c:167-188` เทียบกับ `components/esp_hw_support/mac_addr.c:366-381`) มีผลเฉพาะ option AP
- **R11:** `esp_task_wdt_reset()` ที่เรียกจาก task ที่ไม่ได้ subscribe จะ log error ทุกรอบ (`src/tbft_libbyz.c:806-808`, `src/tbft_replica.c:998-1000`) ตัวอย่างทั้งสอง subscribe แล้ว

- **AGENT.md, anti-replay:** เขียนว่า New_key แต่ละครั้งสร้าง key ใหม่ แต่จริงๆ key สร้างครั้งเดียวต่อการบูต แล้วส่งซ้ำเดิม (`src/tbft_replica.c:2514-2550`) แก้แค่คำอธิบาย ยังไม่เปิด timestamp anti-replay
- **AGENT.md:**
  - local id ไม่ได้ fallback เป็น 0 จริงๆ คือตรวจหาเองอัตโนมัติ ถ้าไม่พบก็ล้มเหลว
  - timer ไม่ได้ถูก start ทั้งหมดตอน init มีเฉพาะ stimer
- **ARCHITECTURE.md:**
  - default ของ checkpoint interval เขียนว่า 128 แต่จริงคือ 8
  - reply size เขียนว่า 1240 แต่จริงคือ 1136
  - signature ของ `Byz_init_replica` ขาด `local_id`
  - คำอธิบาย `Byz_print_stats` ไม่ตรงกับปัจจุบัน
- **FIX_PLAN:**
  - ตารางจำนวนข้อความต่อ request เป็นของก่อน C7: primary ส่ง 13 ไม่ใช่ 19 และ backup รับ 13 ไม่ใช่ 14
  - New_key มีขนาด 1848 B
  - New_key ทุก 60 s ต้องมี key ครบ 6 ตัว ไม่ใช่ 4
  - ตารางนี้ยังถูกใช้เป็นเกณฑ์ตรวจรับ
- **README (root):** ค่าที่แนะนำสำหรับ ESP32-C3 แบบประหยัด (`TBFT_MAX_MESSAGE_SIZE=1024`) build ไม่ผ่าน และ New_key ส่งไม่ได้ ส่วน simple_wallet ที่อ้างถึงใช้ 1248 และ window 16 จริงๆ
- **`gen_configs.sh`:** บรรทัดท้ายบอกให้แก้ `config_espnow.txt` ตรงๆ และให้ build firmware แยก replica กับ client ซึ่งขัดกับ README และ script เขียนทับไฟล์นั้นทุกครั้งที่รัน
- **`sdkconfig.defaults:21`:** เขียนว่า New_key 1840 B ที่ถูกคือ 1848 B

## ลำดับการแก้ที่แนะนำ

1. **ก่อนวัดบนบอร์ด:** X2, X1, X3, X4, X5, X6 (guard) และ X7 กลุ่มนี้กระทบความถูกต้องของผลวัดโดยตรง และไม่แตะ logic ของ PBFT
2. **ความเสถียร:** L1, L2, L3, L6, L7, L9, ส่วน escalation ของ L4 และ R1 ทดสอบด้วย simulator ดังนี้:
   - S3b ที่ loss 12–20% ตาม seed ด้านล่าง
   - scenario ใหม่ที่ kill สองตัวระหว่างที่มีตัวหนึ่งกำลัง fetch
   - Meta_data ซ้ำ
3. **ที่เหลือ:** ข้อระดับต่ำและเอกสาร

## ทำซ้ำผลใน simulator

รันใน shell ที่ไม่ได้ source IDF (ดู `tests/sim/README.md`):

```bash
python3 tests/sim/run.py --seed 104 --env SIM_LOSS=0.15 S3b      # L1: liveness FAIL
python3 tests/sim/run.py --seed 209 --env SIM_LOSS=0.15 S3b      # L1: วนไปถึง view 20
python3 tests/sim/run.py --seed 211 --hw-timeouts --env SIM_LOSS=0.2 S6b   # L2, L4
python3 tests/sim/run.py --seed 407 --env SIM_LOSS=0.05 S3r      # L6
```
